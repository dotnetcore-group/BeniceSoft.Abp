# 消息与事务

作业队列使用 `BeniceSoft.Abp.Extensions.RabbitMQ`。分布式事件、TCC、SAGA 使用 DTM，配置节 `EventBus`。

## RabbitMQ 作业队列

`DependsOn(typeof(BeniceSoftAbpRabbitMqModule))`。连接使用 ABP `RabbitMQ:Connections`。队列名在代码中指定。

```csharp
context.Services.AddRabbitWorkConsumer<OrderImportMessage, OrderImportHandler>(options =>
{
    options.QueueName = "order.import";
    options.PrefetchCount = 10;
});

public class OrderImportHandler : IRabbitMessageHandler<OrderImportMessage>
{
    public Task<RabbitMessageResult> HandleAsync(
        OrderImportMessage message,
        IReadOnlyBasicProperties properties,
        CancellationToken cancellationToken = default)
        => Task.FromResult(RabbitMessageResult.Success);
}
```

`RabbitMessageResult`：

| 值 | 行为 |
|----|------|
| `Success` | ACK |
| `Requeue` | 立即重新入队 |
| `Redelivery` | 投到队列尾部 |
| `DeadLetter` | 拒绝，不入队 |

瞬时失败抛 `RabbitTransientException`。进死信抛 `RabbitDeadLetterException`。也可继承 `RabbitMessageHandlerBase<T>`，由基类映射这两种异常。

`PrefetchCount` 是通道未 ACK 上限，默认 1。大于 1 时同一 Handler 并发处理。`MaxRedeliveryTimes <= 0` 表示不限制 Redelivery 次数。`ConnectionName` 对应 `RabbitMQ:Connections` 中的连接名，默认 `Default`。

```csharp
using var publisher = serviceProvider.CreateWorkPublisher("order.import");
await publisher.PublishAsync(message); // 直接发到 RabbitMQ，不经发件箱
```

Fanout / Direct / Topic：`RabbitRelational.Fanout` / `Direct` / `Topic`，再 `CreatePublisher(relational)`。

### 可靠投递（发件箱 / 收件箱）

需要「业务库事务提交后才真正发消息」时，依赖 `BeniceSoftAbpRabbitMqEntityFrameworkCoreModule`（包 `BeniceSoft.Abp.Extensions.RabbitMQ.EntityFrameworkCore`）。该模块已依赖 `BeniceSoftAbpRabbitMqModule`。

用法与 DTM barrier 类似：**不改宿主 DbContext、不加迁移**。首次使用时按数据库提供程序自动执行 `CREATE TABLE IF NOT EXISTS`（MySQL / PostgreSQL / SQL Server / SQLite）。

```csharp
[DependsOn(typeof(BeniceSoftAbpRabbitMqEntityFrameworkCoreModule))]
public class XxxHostModule : AbpModule { }

// 业务代码须在 UoW 内；与业务写库同一连接 / 事务
await _outbox.PublishToQueueAsync("order.import", batch);
// 或：await _outbox.PublishAsync(RabbitRelational.Work("order.import"), batch);
```

| 类型 | 作用 |
|------|------|
| `IRabbitOutboxPublisher` | 当前 UoW 内写入发件箱表；UoW 提交后由后台派发器发到 RabbitMQ；回滚则不会发出 |
| `IRabbitInboxStore` | 消费端幂等存储；由 `options.Idempotent = true` 启用 |
| `IRabbitDeadLetterReplayer` | 运维：把死信队列消息移回原队列 |

消费端可选能力：

```csharp
context.Services.AddRabbitWorkConsumer<OrderImportMessage, OrderImportHandler>(options =>
{
    options.QueueName = "order.import";
    options.Idempotent = true;                 // MessageId + 消费者名去重
    options.MaxExceptionRetryTimes = 3;        // 未处理异常重试次数，默认 3；-1 = 旧行为（无限 requeue）
    options.RetryExhaustedAction = RabbitRetryExhaustedAction.Auto; // Auto / DeadLetter / Drop
    options.Relational = RabbitRelational.Work(
        new RabbitQueueDeclare { Name = "order.import" }
            .SetDeadLetter(string.Empty, "order.import.dlq"));
});
```

- `Idempotent`：需已依赖 EF 模块。发布端会自动填 `MessageId`（也可自行指定）。
- `MaxExceptionRetryTimes`：Handler 抛未处理异常时带重试头重新投到本队列；次数用尽按 `RetryExhaustedAction` 处理。`Auto`：队列声明了 `x-dead-letter-exchange` 则进死信，否则记错误日志后 ACK 丢弃。`MaxRedeliveryTimes` 用尽时同样走该策略。
- 死信重放：`await replayer.ReplayAsync("order.import.dlq", 100);`。不传目标队列时从 `x-death` 读原队列。

`RabbitOutboxOptions`（`Configure<RabbitOutboxOptions>`）：

| 项 | 说明 |
|----|------|
| `DbContextType` | 派发器 / 收件箱使用的 DbContext。宿主只注册一个时自动识别；**多个 DbContext 时必须显式指定** |
| `Schema` / `OutboxTableName` / `InboxTableName` | 表名，默认 `rabbit_outbox_messages`、`rabbit_inbox_messages` |
| `DispatcherEnabled` | 是否在本进程跑派发器，默认 `true` |
| `BatchSize` / `PollingInterval` / `LockTimeout` | 批大小、空闲轮询、行租约（多实例防重发） |
| `MaxRetryCount` / `RetryBaseDelay` / `RetryMaxDelay` | 发往 broker 失败时的退避 |
| `SentRetention` / `InboxRetention` / `CleanupInterval` | 已发送行与收件箱行的清理 |

发件箱写入始终优先使用**当前 UoW 中已打开的业务 DbContext**（与业务写库同一事务）。派发器只扫描 `DbContextType` 对应库。

### 与 DTM / EventBus 的分工

| 场景 | 选用 |
|------|------|
| 平台拉单、批量导入、后台作业等点对点队列 | RabbitMQ 作业队列；需与业务同事务时用发件箱 |
| 服务间领域事件、ABP `IDistributedEventBus` | DTM + `EventBus:Type=DTM` |
| 跨服务 TCC / SAGA | DTM |

二者可同时依赖。作业队列不替代 EventBus；发件箱只管本服务发到 RabbitMQ 的可靠投递。

## DTM

`BeniceSoftAbpEventBusDtmHttpModule` 处理 HTTP 回调。`BeniceSoftAbpEventBusDtmEntityFrameworkCoreModule` 提供 outbox / inbox。

```json
"EventBus": {
  "Type": "DTM",
  "DTM": {
    "AppUrl": "http://gateway:5056",
    "DtmUrl": "http://dtm:36789",
    "DbContextName": "WarehouseCenterDbContext"
  }
}
```

`AppUrl` 是 DTM 回调本服务的地址。经网关时填网关地址，`[DtmBranch].ServiceName` 与 `ServiceDiscovery:ServiceName` 相同。`DbContextName` 为本服务 DbContext 类名。

`UseDtmHttpMiddleware()` 放在认证之前。回调路径：`/dtm_boxes.DtmHttpService/tcc`、`/dtm_boxes.DtmHttpService/saga`。

`EventBus:Type` 为 `DTM` 时，`IDistributedEventBus.PublishAsync` 走 outbox。

### TCC

请求实现 `IBranchRequest`，并标记 `[DtmBranch(serviceName, handlerName)]`。Handler 实现 `ITccBranchCallbackHandler<TRequest>`：`TryAsync`、`ConfirmAsync`、`CancelAsync`。

```csharp
[DtmBranch("order-service", "order-create")]
public class CreateOrderRequest : IBranchRequest
{
    public string BizId { get; set; } = string.Empty;
}
```

```csharp
context.Services.AddDtmCallbackHandlersFromAssemblies(typeof(CreateOrderHandler).Assembly);

await globalTransaction.ExecuteTccAsync(async tcc =>
{
    await tcc.CallBranchAsync(new CreateOrderRequest { BizId = bizId });
});
```

`CallBranchAsync` 未传 `serviceName` / `handlerName` 时，从 `[DtmBranch]` 读取。Try 阶段抛异常后，DTM 调用 Cancel。

TCC 编排器先 Prepare，再依次调用 Try；业务成功后 Submit，业务异常或取消后 Abort。Confirm、Cancel 由 DTM 调度。Submit 请求发出后若响应异常，应按 gid 查询最终状态，不能因为调用方没有收到成功响应就擅自改为 Cancel。

### 回调事务与屏障

TCC、Saga 回调使用接收服务 `EventBus:DTM:DbContextName` 对应的本地 DbContext。发起服务的 DbContext 类型、连接串哈希不作为接收端选库依据；MSG 的来源库定位机制保持不变。

每个回调的屏障和业务写库必须使用同一 DbContext、连接和本地事务。多库业务应拆成各自的事务分支。缺少接收端 DbContext 配置时回调明确失败，不跳过屏障继续执行业务。

Cancel 会为 Try 插入占位，Compensate 会为 Action 插入占位。空补偿提交占位并跳过业务，迟到正向请求及重复请求同样跳过业务；业务失败则连同本次屏障一起回滚。

Try、Action 抛出 `BusinessException` 表示确定的业务拒绝，回调返回 HTTP 409 和 `FAILURE`。其他异常返回 HTTP 500；Confirm、Cancel、Compensate 的异常保持可重试，不把未完成的补偿当作成功。

### SAGA

请求同样实现 `IBranchRequest` 并标记 `[DtmBranch]`。Handler 实现 `ISagaBranchCallbackHandler<TRequest>`：`ActionAsync`、`CompensateAsync`。

```csharp
await globalTransaction.ExecuteSagaAsync(saga =>
{
    saga.AddBranchByHandler(request);
    return Task.CompletedTask;
});
```

`AddDtmCallbackHandlersFromAssemblies` 同时注册 TCC 与 SAGA Handler。

Saga 只调度已经注册的 Action、Compensate，不会自动恢复发起方任意已提交的数据。订单状态等需要补偿的修改应放到 Action 分支，并在 Compensate 中实现对应业务撤销。

### 可持久化样例

SampleHost 的订单、库存演示使用 `sample_transaction_orders`、`sample_transaction_inventories` 两张独立样例表。先手工执行 [初始化脚本](../samples/sql/transaction-sample-init.sql)，不通过宿主启动自动迁移业务表。

样例库存按 BizId 独立初始 10 件，不操作共享 SKU 库存。两个演示入口都支持指定 `bizId`，并使用该值作为 DTM gid：

- `POST /api/sample/distributed-event-sample/test-tcc-two-services-style?bizId=唯一编号&simulateBizFailure=false`
- `POST /api/sample/distributed-event-sample/test-saga?bizId=唯一编号&simulateBizFailure=false`
- `GET /api/sample/distributed-event-sample/transaction-state/唯一编号`

TCC 成功后订单、库存均为 `Confirmed`，可用 9、冻结 0、已扣 1；模拟失败后两者均为 `Cancelled`，可用库存恢复 10。Saga 成功后两者均为 `Applied`；模拟库存业务拒绝后，订单为 `Compensated`，库存正向事务未提交，因此空补偿不创建库存行。

样例调用显式指定 `serviceName: "/"`，适用于 `AppUrl` 直接指向 SampleHost。经 Gateway 部署时，`AppUrl` 指向 Gateway，并使用 `[DtmBranch]` 中实际注册的服务名；不要把带服务名前缀的地址直接发到未提供该前缀路由的宿主。

每次演示使用新的 BizId。确认事务终态后，可使用 [按 BizId 清理脚本](../samples/sql/transaction-sample-cleanup.sql) 删除本次样例业务数据；不要提前删除屏障记录，以免迟到请求重新执行业务。
